At Tata Consultancy Services, I inherited a forecasting model that was technically working — 78% accuracy, shipped, in production. Nobody was thrilled with it, but nobody was rewriting it either. That's the most dangerous state a model can be in.

<Callout type="info" title="Context">
  The pipelines behind this sat on top of 500GB+ of enterprise data processed daily through Azure Data Factory, feeding operational and financial dashboards across multiple business units.
</Callout>

## Why 78% wasn't good enough

The model was consuming raw transactional fields more or less as they came off the source systems — a handful of aggregates, a couple of lag features, and not much else. It captured the obvious seasonality but missed the second-order signals: interaction effects between regions and product categories, rolling volatility, and how recent an anomaly was before it started dragging predictions off course.

## Feature engineering, not model swapping

The instinct when a model underperforms is to reach for a fancier algorithm. I didn't. Instead I built out a feature engineering pipeline that expanded the input space from a dozen raw fields to over 100 engineered features — rolling statistics at multiple windows, categorical interaction terms, and decay-weighted historical aggregates.

```python
import pandas as pd

def engineer_rolling_features(df: pd.DataFrame, windows=(7, 14, 30)) -> pd.DataFrame:
    df = df.sort_values("date")
    for w in windows:
        df[f"rolling_mean_{w}d"] = (
            df.groupby("category")["value"]
              .transform(lambda s: s.rolling(w, min_periods=1).mean())
        )
        df[f"rolling_std_{w}d"] = (
            df.groupby("category")["value"]
              .transform(lambda s: s.rolling(w, min_periods=1).std())
        )
    return df
```

<Callout type="tip" title="Where the gains actually came from">
  The rolling volatility features (`rolling_std`) ended up mattering more than the mean features — spikes in variance were an earlier warning signal than the level of the series itself.
</Callout>

## Validation had to come first

None of this matters if the input data is unreliable. Before trusting any new feature, I put a validation framework in front of the pipeline — schema checks, null-rate thresholds, and range assertions across datasets exceeding 1M+ records, catching bad batches before they reached the model rather than after.

| Stage | Metric | Before | After |
|---|---|---|---|
| Data validation | Accuracy across datasets | — | 99.9% |
| Feature engineering | Model AUC | 0.71 | 0.86 |
| Forecasting model | Prediction accuracy | 78% | 92% |
| Anomaly detection | Detection accuracy | — | 95% |

## What I'd tell someone starting this today

Model accuracy problems are usually feature problems wearing a model-shaped disguise. Before reaching for a different algorithm, ask whether the model actually has access to the signal you're expecting it to learn. In this case, it didn't — and once it did, 92% wasn't a stretch, it was just what the data had been saying all along.
